# Протокол ручной разметки (ground truth), черновик

Зачем нужен: ручная разметка задаёт «правильный ответ», с которым сравниваются система и axe-core.
Чтобы разметка не выглядела мнением автора, определения нарушений берутся из опубликованных
источников, а порядок работы исключает влияние вывода детектора.

## 1. Что проверяется (определения по наблюдаемым фактам)

### Модальное окно (источники: ARIA APG «Dialog (Modal)», техника WCAG F85)
- **M1.** После открытия клавиатурой `document.activeElement` находится внутри диалога.
  Нарушение: `focus_not_moved_into_modal`.
- **M2.** Tab и Shift+Tab не переводят фокус на содержимое страницы за диалогом.
  Уход фокуса в интерфейс браузера (на `body`) утечкой не считается: решение авторов, потому что
  интерфейс браузера не является содержимым страницы, а нативный `<dialog>` ведёт себя именно так.
  Это решение указывается в угрозах валидности.
  Нарушение: `focus_leaks_out_of_modal`.
- **M3.** После закрытия фокус вернулся на элемент, открывший диалог (если он удалён, на логичный элемент).
  Нарушение: `focus_not_restored`.
- Дополнительно записывается в заметки: закрывается ли диалог клавишей Escape.

### Смена маршрута (источники: документация React Router, исследование Gatsby/Fable Tech Labs)
- **R1.** После клиентской навигации фокус перенесён в новый контент (заголовок, `main`, обёртка).
- **R2.** Либо обновился live-регион (`aria-live`, `role=status|alert|log`), объявляющий смену страницы.
  Смена `document.title` фиксируется отдельно и компенсирующей мерой не считается, пока не подтверждена
  проверкой скринридером.
- Нарушение: нет ни R1, ни R2. Типы: `focus_reset_to_body`, `focus_stayed_on_trigger`.
- Пока детектор не учитывает R2 в вердикте, наличие R2 отмечается в заметках вручную.

### Динамическая подгрузка (источники: WCAG 2.4.3; таксономия «потеря фокуса после активации» в A11yLTLNav)
- **D1.** После вставки нового контента фокус не потерян (`activeElement` не `body`).
- **D2.** Следующий Tab идёт на следующий элемент в порядке DOM, без возврата назад.
- Нарушения: `focus_lost_after_load`, `tab_order_not_monotonic`.

## 2. Порядок разметки одного сценария

1. Открыть приложение в обычном Chrome. В консоли добавить live expression `document.activeElement`.
2. Не перезагружать страницу между шагами сценария.
3. Выполнять действие **только клавиатурой**.
4. Записывать, где стоит `activeElement` после каждого шага.
5. Сравнить с определениями из раздела 1 и внести строку в `ground-truth.csv`.
6. Заполнить колонки: `set` (real/fixture), `annotator`, `annotated_before_detector`, `notes` (что именно наблюдалось).

## 3. Защита от влияния детектора

- Сценарий размечается **до** запуска детектора на нём. Колонка `annotated_before_detector` = `yes`.
- Если оценка менялась после просмотра вывода детектора, ставится `no`, а причина записывается в `notes`.
  (Пример: `modal-good` изменён после вывода детектора.)
- Пересмотр разметки допустим только с записью даты и причины.

## 4. Второй разметчик

- Независимо размечает не менее 30% сценариев (если корпус мал, то все), не видя первую разметку.
- Считается κ Коэна: κ = (po − pe) / (1 − pe), где po доля совпадений, pe ожидаемая доля случайных совпадений.
  Пример: совпали 18 из 20, оба ставят «да» в половине случаев: po = 0.9, pe = 0.5, κ = 0.8.
- Ориентир по шкале Лэндиса и Коха: 0.61–0.80 значительное согласие, 0.81 и выше почти полное.
- Расхождения разбираются с научным руководителем, решение записывается.

## 5. Выборочная проверка скринридером

Для 10% сценариев (особенно роутинга) проверка в NVDA (Windows) или VoiceOver (macOS):
озвучивается ли смена страницы. Результат записывается в `notes`.
